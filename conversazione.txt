The error you pasted — [tool_call bridge refused] params must have required property 'name' — comes from a deferred tool-call bridge (as seen in Qwen Code and similar frameworks).  It means the envelope sent to tool_call was missing the required top-level name field. The bridge expects:

{

  "arguments": { ... }
}

Your payload {"query":"select:"} has neither name nor arguments at the top level, so the Ajv schema validator rejects it before the target tool is even resolved.

Diagnosed Qwen Code tool schema mismatch
Il problema è che qwen2.5:7b è troppo piccolo per gestire affidabilmente il pattern a due step tool_search → tool_call di Qwen Code. Il modello confonde il campo name dell'envelope con tool_name o lo omette del tutto.

Cause
Modello 7B — il tool calling structured è inaffidabile sotto i ~14B, soprattutto con un envelope a due livelli.
num_ctx di default Ollama = 2048 — il system prompt e le definizioni dei tool vengono troncato, quindi il modello "dimentica" lo schema corretto. 
È un bug noto ( #14216 ): l'errore params must have required property 'name' non chiarisce che si tratta dell'envelope del bridge, non dello schema del tool target, quindi il modello non sa come correggersi. 
Soluzioni
Priorità	Azione	Dettaglio
1	Cambia modello	qwen2.5-coder:7b (variante coder, molto migliore nel tool calling) o meglio ancora qwen3-coder:30b / qwen3:8b
2	Aumenta il contesto Ollama	OLLAMA_CONTEXT_LENGTH=32768 (o 65536) nell'ambiente, oppure deriva un modello con num_ctx più grande: ollama create qwen2.5-32k -f Modelfile con PARAMETER num_ctx 32768
3	Bypassa il bridge	In ~/.qwen/settings.json aggiungi i tool che ti servono in tools.visible — così vengono dichiarati direttamente nella request e il modello li chiama senza passare per tool_search/tool_call:

{
  "tools": {
    "visible": ["find_files", "read_file", "shell"]
  }
}

Con tools.visible il modello invoca il tool direttamente (es. find_files(pattern: "…")) e l'envelope a due livelli non esiste più — il 7B gestisce senza problemi.

TL;DR
Il 7B non è abbastanza capace per il deferred-tool bridge. Usa qwen2.5-coder:7b (minimo) o qwen3-coder:30b (consigliato), alza num_ctx a ≥ 32k, e se vuoi restare sul 7B metti i tool frequenti in tools.visible per evitare il bridge.

🔍 Elenco degli strumenti Qwen Code
Ecco l'elenco completo dei tool disponibili in Qwen Code, divisi per categoria. 

Eager (già attivi di default, non vanno in tools.visible)
Tool	Funzione
read_file	Legge un singolo file
write_file	Crea/sovrascrive un file
edit	Modifica diff-based
glob	Trova file per pattern
grep_search	Cerca testo con regex
run_shell_command	Esegue comandi shell

Questi sono già nella request iniziale — non vanno in tools.visible.

Deferred (vanno in tools.visible se li vuoi attivi)
Tool	Funzione
read_many_files	Legge più file/directory in batch
web_fetch	Recupera contenuto da un URL
web_search	Cerca su web (serve un provider di ricerca)
save_memory	Salva/ricorda info tra sessioni
todo_write	Crea e gestisce liste di task strutturate
monitor	Comandi shell long-running con streaming
agent	Delega task a sub-agent specializzati
enter_plan_mode	Entra in modalità pianificazione
exit_plan_mode	Esce dalla modalità pianificazione

Raccomandato per programmazione
"tools": {
  "visible": [
    "read_many_files",
    "todo_write",
    "monitor"
  ]
}

read_many_files — utile quando il modello deve analizzare più file insieme (es.  "leggi tutti i file della cartella src/")
todo_write — il modello crea una checklist di task e la aggiorna mentre lavora; molto utile per task multi-step
monitor — per comandi che restano attivi a lungo (es.  npm run dev, server in background)
web_fetch e web_search li puoi aggiungere se il modello deve consultare documentazione online, ma con Ollama locale web_search non funziona (serve un provider di ricerca configurato). agent è avanzato e con un 8B potrebbe confondersi.

Nota
Puoi verificare in qualsiasi momento i tool attivi digitando /tools dentro una sessione Qwen Code.
